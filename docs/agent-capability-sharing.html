Shared Agent Capabilities with APM
Working proposal | Data and analytics engineering | September 2026

Purpose of this document

A practical model for sharing agent skills, system connections, and team workflows

This proposal explains how Agent Package Manager (APM) could be used to maintain a versioned internal library of agent capabilities. It focuses on how packages are structured, how employees receive the right capabilities, how access remains controlled, and how the team contributes improvements.

1 | Problem to solve

Agent capability is currently difficult to reuse consistently

People can create useful prompts, instructions, scripts, and connectors, but these often remain in personal configurations or individual project repositories. A colleague must rediscover the same setup and lessons.

Knowledge is fragmented

Platform-specific lessons are spread across documentation, code, chat history, and individual agent configuration.

Setup is repeated

Each person configures skills and MCP servers separately for each agent tool and project.

Quality varies

There is no common review, version, ownership, or retirement process for agent guidance.

Onboarding depends on people

New employees need colleagues to explain which tools, conventions, and access patterns apply to their role.

Proposed outcome

A person should be able to install an approved role package and receive the same reviewed skills, instructions, commands, agents, and MCP declarations as the rest of the team.

2 | What is shared

The package contains several different capability types

These terms are related but not interchangeable. A useful package may contain only one or two of them.

Component What it provides Example
Skill A focused workflow the agent loads when the user's request matches its description. Discover a Fabric table and verify its schema before writing SQL.
Instruction A rule that applies automatically, globally or to particular file types. Use explicit PySpark schemas and never infer production schemas.
MCP server A declared connection that exposes approved tools or data to the agent. Read Fabric metadata or query an approved Databricks interface.
Script Deterministic automation used when exact behavior is more reliable than generated steps. Validate a notebook, inspect a wheel, or check for hard-coded IDs.
Named agent A specialist role with a defined task, expected output, and optional tool restrictions. A read-only release reviewer or pipeline troubleshooter.
Command An explicitly invoked, repeatable procedure exposed in a supported agent client. Run a standard pre-release validation and summarize failures.
Profile An APM package that depends on a curated combination of the components above. "Profile" is our organizational term, not a separate APM primitive. Data engineer, Fabric engineer, or Databricks application developer.

3 | How APM works

One manifest is translated into the configuration each agent tool expects

APM is a dependency manager for agent configuration. It uses a committed apm.yml manifest and creates an apm.lock.yaml lockfile that records exactly what was resolved.

STEP 1

Author

Teams store packages and profiles in Git with normal pull-request review.

STEP 2

Install

apm install resolves dependencies, checks content, and writes client files.

STEP 3

Lock

The lockfile pins source commits and hashes for reproducible installation.

STEP 4

Compile

apm compile builds root context such as CLAUDE.md and AGENTS.md.

Commands a consumer runs

# Install the approved profile into a project
apm install company/agent-capabilities/profiles/data-engineer#v1.2.0 \
  --target claude,opencode

# Compile shared instructions for both clients
apm compile --target claude,opencode

# Confirm installed MCP declarations and package integrity
apm mcp list
apm audit

What APM writes

Source in package Claude Code OpenCode
.apm/skills/ .claude/skills/ .agents/skills/
.apm/instructions/ .claude/rules/ and compiled context Compiled into AGENTS.md
.apm/agents/ .claude/agents/ .opencode/agents/
.apm/prompts/ .claude/commands/ .opencode/commands/
dependencies.mcp .mcp.json opencode.json
Install and compile are separate

apm install resolves and deploys package primitives. apm compile generates root instruction context. A standard setup script should run both in the correct order.

4 | Repository model

A private Git repository can hold reusable packages and role profiles

The first version can use one private repository. Access to the repository controls who can install private capability content. More sensitive packages can later move to separate repositories with narrower permissions.

Illustrative structure

Recommended initial boundary

Content Placement Reason
Generic skill authoring, review, Git, and testing guidance Core package Applicable across teams and platforms
Fabric, Databricks, Synapse, and SAP workflows Platform packages Independent ownership and specialist review
Internal endpoints, governed metadata, business-specific instructions Private restricted package Needs tighter repository access and review
Credentials, tokens, personal data, production records Never in a package Remain in identity systems, secret stores, or user environment

5 | Role profiles

A profile selects a useful set of capabilities for a role

A profile is an ordinary APM package whose main purpose is composition. It can depend on shared packages and declare the MCP servers required for that role.

Example profile manifest

name: company-data-engineer
version: 1.2.0
description: Approved baseline for data engineers.

targets:
  - claude
  - opencode

dependencies:
  apm:
    - git: https://github.com/company/agent-capabilities.git
      path: packages/core
      ref: ^1.0.0

    - git: https://github.com/company/agent-capabilities.git
      path: packages/fabric
      ref: ^1.2.0

    - git: https://github.com/company/agent-capabilities.git
      path: packages/databricks
      ref: ^1.1.0

  mcp:
    - name: fabric-metadata
      registry: false
      transport: http
      url: https://mcp.internal.example/fabric
      headers:
        Authorization: "Bearer ${FABRIC_MCP_TOKEN}"
The URL and token name above are placeholders

The real authentication model must be approved for each MCP server. Tokens are not committed to the profile. APM uses environment-variable indirection or target-native authentication where supported.

Possible profiles

Profile Likely package dependencies Likely connections
Data engineer Core, Fabric, Databricks, SQL, CI/CD Metadata and read-only platform tools
Fabric engineer Core, Fabric notebooks, pipelines, deployment Fabric metadata, approved SQL endpoint access
Analytics developer Core, SQL, semantic model and report validation Catalog and read-only analytics metadata
Platform reviewer Core, security review, release validation Read-only repository and platform evidence

6 | Employee onboarding

The agent setup can be reproduced in minutes after access is approved

This does not replace account creation, platform training, or access approval. It reduces the manual work of locating and configuring the team's agent capabilities after those prerequisites are available.

Prerequisites owned by existing processes

  • Company identity and device setup
  • Repository access
  • Platform roles for Fabric, Databricks, Synapse, or SAP
  • Claude Code or OpenCode installation
  • Authentication for approved MCP services

Agent capability setup

# 1. Authenticate to private Git hosting
gh auth login

# 2. Install the role profile
apm install company/agent-capabilities/profiles/data-engineer#v1.2.0 \
  --target claude,opencode

# 3. Build root instructions
apm compile --target claude,opencode

# 4. Verify the result
apm audit
apm mcp list

Example onboarding sequence

Role selected

The manager or technical lead assigns the approved data-engineer profile.

One installation

APM installs the same pinned capabilities used by colleagues and writes the correct files for the selected agent tools.

Connections verified

The employee authenticates separately. A read-only test confirms what the agent can and cannot access.

Guided first task

The employee uses a known skill on a low-risk task and compares the result with the team's expected workflow.

Normal work begins

The employee has a documented baseline without copying configuration from another person's machine.

What "minutes" means

The package installation and configuration can be short. Waiting for platform permissions, completing training, and learning the business domain remain separate onboarding activities.

7 | Versioning and updates

Git tags describe available versions; the lockfile records the exact installed content

A profile can request an exact tag or a compatible version range. APM resolves that request to a specific commit and records the result in apm.lock.yaml.

Item Purpose Example
Package version States the version published by the package owner version: 1.2.0
Git tag Marks released source in the repository v1.2.0
Dependency constraint Defines which releases a profile accepts ref: ^1.2.0
Lockfile Pins the resolved tag, commit, and content hash apm.lock.yaml

Recommended first approach: lockstep releases

For a small initial repository, release all packages and profiles together under one version. This is simpler to explain, test, and support. Independent package versions can be introduced later if release cycles genuinely diverge.

1

Change merged

A reviewed capability change reaches the release branch.

2

Version tagged

CI validates and publishes a new Git tag, for example v1.3.0.

3

Existing users stay pinned

Their lockfile keeps the previous known version until they update.

4

Update is deliberate

apm install --update resolves and records the approved newer version.

Recommended project policy

Commit apm.yml and apm.lock.yaml. Ignore apm_modules/. Decide centrally whether generated client files are committed or reproduced during setup and CI; apply one policy consistently.

8 | How people contribute

Contribution uses the same Git and pull-request practices as code

The goal is broad contribution with clear ownership. A subject-matter expert should be able to propose a capability without becoming the sole approver or long-term support contact by accident.

Contribution path

  1. Describe a repeated task and provide realistic trigger examples.
  2. Choose the right component: skill, instruction, script, MCP declaration, or profile change.
  3. Create a branch from a template and add tests or manual scenarios.
  4. Open a pull request with scope, risk, evidence, and ownership.
  5. Receive technical and platform/security review as required.
  6. Merge into the next version and update release notes.

Minimum review checklist

  • A real repeated problem is identified
  • Triggers and non-triggers are tested
  • Examples contain no secrets or sensitive records
  • Side effects and required approvals are explicit
  • Claude Code and OpenCode placement is validated
  • An owner and review date are recorded

Suggested ownership

Role Responsibility
Contributor Provides the use case, initial content, examples, and validation evidence.
Capability owner Maintains scope, quality, compatibility, versions, and retirement decisions.
Platform reviewer Checks technical correctness for Fabric, Databricks, Synapse, SAP, or another system.
Security reviewer Reviews new MCP servers, credentials, data exposure, executable scripts, and side effects.
Repository maintainer Manages releases, CI, package structure, and contribution standards.

9 | Access and governance

Sharing configuration does not grant system access

The package may describe a connection, but each platform still authorizes the signed-in user or service identity. This separation should remain explicit in documentation and testing.

Repository access

Controls who can read and install private capability content.

Platform identity

Controls which Fabric, Databricks, Synapse, or SAP resources a user can access.

MCP tool scope

Controls which functions the server exposes. Tool allowlists should be used where practical.

Production controls

CI/CD approvals and platform permissions remain authoritative for material actions.

MCP is a trust boundary

An MCP server exposes tools or data to the agent and requires its own owner, threat review, authentication model, logging, support, and retirement plan. APM intentionally restricts untrusted transitive self-defined MCP declarations unless the consumer explicitly trusts them.

Non-negotiable rules

  • No credentials, tokens, connection strings, or production records in packages.
  • Read-only tools are the default for initial platform integrations.
  • Material writes require explicit user confirmation and existing platform authorization.
  • Agent hooks provide convenience, not the only enforcement for tests or security.
  • Every executable script and MCP server has a named owner.

10 | Current limitations

The model is portable, but not every feature is identical across agent tools

Limitation Practical treatment
Claude Code and OpenCode use different native file locations and formats. Keep neutral source under .apm/ and let APM deploy per target.
APM hooks do not currently target OpenCode. Use a shared script with separate Claude hook and OpenCode plugin adapters only when automatic behavior is needed.
Self-defined MCP servers are executable trust boundaries. Keep them direct, documented dependencies and require explicit security review.
A skill can become stale or conflict with another skill. Use owners, versions, trigger tests, usage feedback, and retirement dates.
Package installation cannot provide business understanding. Use profiles to support, not replace, training, mentoring, and domain documentation.
APM is still evolving. Pin the supported APM version, test upgrades, and avoid making governance dependent on undocumented behavior.

11 | Suggested pilot

Test the complete sharing process with a small, read-only scope

The pilot should test authoring, review, installation by another employee, update behavior, and measurable task value. It should not attempt to build all platform packages at once.

Pilot item Suggested scope
Profile One data-engineer profile targeting Claude Code and OpenCode
Core capability Skill authoring and contribution workflow
Work capability 1 Metadata-first Fabric SQL and schema discovery
Work capability 2 Thin notebook and shared Python library guidance
MCP One approved read-only metadata connection
Users Original author plus two employees who did not build the package
Evidence Setup time, task time, successful reuse, quality findings, and security exceptions

Questions for management

  1. Which two repeated tasks are important enough to test first?
  2. Who should own the common repository and approve platform-specific content?
  3. Which private Git host and access model should be used?
  4. Which MCP connection can be approved for a read-only pilot?
  5. What evidence would justify extending the approach to more teams and platforms?
Concrete pilot deliverable

A second employee can install the pinned data-engineer profile in a clean project, verify the approved MCP connection, use both work skills successfully, and later update to a new reviewed version without manual file copying.
